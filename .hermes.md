# Deterministic Writing Runtime — Hermes Project Contract

This repository is a deterministic fiction-control workspace. The model may propose plans and prose; Python owns canon, narrative state, validation, retry budgets, disclosure isolation, acceptance, and salvage.

## Hard rules

1. For an end-to-end writing request, Hermes should operate conversationally but delegate the actual recursive writing loop to `writing-pilot` / `pilot_controller.py`.
2. Interactive Hermes is the operator, not the planner/writer/controller. Do not manually recreate plan -> draft -> critique -> rewrite in the current chat.
3. Never bypass a non-zero gate result by declaring the text acceptable yourself.
4. Never copy raw analyzer messages into a model prompt. Use prompts emitted by the runtime.
5. Never resume a model context across disclosure epochs. The pilot controller uses fresh child Hermes calls for generative phases.
6. Never mutate accepted prose from an unvalidated model response. Apply through runtime contracts/reassembly.
7. If a workflow reaches `human_review`, stop. Do not create another unbounded critique/rewrite loop.

## New user-owned story

The root Mara/Sable Bind canon and state are test fixtures only. If the user asks for a new/my/own pilot, do not use those stores.

Capture the user's own premise/first-chapter brief, title, and POV, then invoke `writing-project-init`. The initializer creates a private local `projects/<slug>/` namespace with its own timeline, source YAML, compiled stores, runtime state, and manuscript directory. It starts sparse: the user-supplied POV is registered as a character, but no invented canon/state history is fabricated.

After successful initialization invoke `writing-pilot --project <slug> --skip-setup`. `projects/` is ignored by the public harness Git repository by default.

## Existing project / fixture

For an existing named story use `writing-pilot --project <slug> --skip-setup` and let `project.json` select that story's authority stores.

Only when the user explicitly asks for the current/example/Mara fixture use `book1/ch05`, branch `main`, viewpoint `Mara`, plan id `pilot.first.ch05`, workdir `runtime_state/pilot-first`.

## GUI rule

Hermes Desktop does not need to start in the harness checkout. `writing-project-init` and `writing-pilot` are installed console commands that resolve the editable harness package. Do not treat GUI CWD as authority and do not silently clone another runtime.

The current interactive session may remain conversational while the controller launches fresh child Hermes processes for planning, disclosure epochs, and repair. Fresh process boundaries—not role names—provide disclosure isolation.

## Temporal v0.7 rule

Treat `timeline_branch` as part of every planning/drafting/repair contract. Never assume `main` after a chronobreak. Do not carry facts/state from a parent after the branch fork unless the deterministic runtime re-injects them. Use the runtime's state/canon surfaces rather than memory when branches disagree.
